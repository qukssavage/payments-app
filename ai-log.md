Инструмент: Claude (claude.ai, десктопное приложение) в роли ментора и ревьюера.
Формат работы: Claude объяснял архитектуру и решения, генерировал код по этапам, давал сценарии ручной проверки; я разбирал код, вносил его в проект, проверял через Swagger (`/docs`), в том числе на ошибочных данных, и коммитил после каждого этапа.

## 2026-10-24

### Разбор ТЗ и план
- Попросил Claude разобрать ТЗ и найти подводные камни.
- Полезный промпт: «прочти ТЗ внимательно и скажи своё мнение» — Claude выделил неочевидные места: ученики без оплат должны попадать в должники, деньги нельзя хранить во float, нужно явно решить про переплату, удаление ученика с оплатами и учеников, добавленных в середине месяца.
- Выбрал вариант Б (веб-страница): проверяющим проще запустить, не нужен токен Telegram.
- Стек: Python + FastAPI + SQLite (встроенный `sqlite3`, SQL вручную, без ORM — чтобы запрос должников был прозрачным).

### Этап 0. Окружение
- Сам: установка, виртуальное окружение, `.gitignore`, git, репозиторий на GitHub, тестовый эндпоинт `/health`.

### Этап 1. Ученики (CRUD)
- Сгенерировано Claude: `database.py` (схема таблиц, подключение), `schemas.py` (валидация Pydantic), CRUD в `main.py`.
- Принятые решения: суммы в INTEGER (сумы); `ON DELETE CASCADE` для оплат; поле `created_at` для учёта даты добавления ученика; PATCH меняет только переданные поля.
- Заранее учтённый подвох: `check_same_thread=False` — FastAPI может выполнять зависимость и эндпоинт в разных потоках, без этого sqlite3 падает.
- Проверил сам через `/docs`: создание (201), список, PATCH, удаление (204), ошибки — отрицательная сумма и неверный телефон (422), несуществующий id (404).

### Этап 2. Оплаты
- Сгенерировано Claude: схемы `PaymentCreate`/`Payment`, эндпоинты `POST /payments`, `GET /students/{id}/payments`.
- Решения: дата оплаты по умолчанию — сегодня; запрет будущих дат и сумм ≤ 0.
- Проверил сам: оплаты создаются; несуществующий ученик → 404; сумма 0 → 422; дата 2030 года → 422.

### Этап 2. Должники
- Сгенерировано Claude: `GET /debtors?month=YYYY-MM` (месяц необязателен, по умолчанию текущий).
- Ключевые ловушки, которые разобрал: `LEFT JOIN` вместо `JOIN` (иначе пропадают ученики без оплат) и фильтр по месяцу в `ON`, а не в `WHERE` (иначе они пропадают снова). Учитываются только ученики, добавленные до конца месяца.
- Проверил сам через `/docs`: за октябрь в списке ученица без оплат за месяц (долг полный, её сентябрьская оплата не засчитана) и ученик с частичной оплатой; неверный формат месяца → 422.
- При проверке обнаружил, что на этапе 1 пропустил ручную проверку PATCH и DELETE. Проверил их на данных должников: после PATCH долг пересчитался, после удаления ученик исчез из списка; каскадное удаление оплат подтвердил (после удаления ученика его оплаты → 404).

## Где ИИ ошибался
- **Часовой пояс в датах.** В первой версии `created_at` ученика заполнялся в SQLite через `date('now')` — это дата по UTC, а дата оплаты бралась в Python через `date.today()` — местное время (Ташкент, UTC+5). Ученик, добавленный 1-го числа до 05:00, получил бы дату предыдущего месяца и попал бы в должники за месяц, когда ещё не учился. Claude нашёл несостыковку сам, когда писал тесты на границы месяца. Исправление: `created_at` теперь задаётся из Python тем же `date.today()`.
